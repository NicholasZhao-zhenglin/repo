# 06 · 项目问答

这些回答只描述本次已实现或明确待做的内容，未声称生产规模或外部用户验证。

## 怎样用两分钟介绍架构？

这是一个个人离线 Electron App。React 负责总览和草稿，preload 暴露有限 API，主进程检查请求、处理图片并把资料保存到 Application Support。JSON 与图片分开存储，写操作串行；备份把资料和图片打进同一个版本化文件。依据：`shared/model.ts`、`electron/main.ts`、`electron/store.ts`。

追问：为什么没有后端？用户明确只在本人电脑使用，账户、网络服务和同步不增加当前价值，却增加部署与数据边界。

## 如何避免两个保存操作相互覆盖？

`ArchiveStore.serial` 把写入排进 Promise 队列，每次从提交后的内存快照构建下一版。单实例锁限制同一 userData 的第二个实例。测试同时创建并收藏 16 位合成角色，确认没有丢记录。依据：`tests/store.test.ts`。不能由此推断支持多个不同程序同时改同一个 JSON。

## 保存过程突然失败，已有角色会怎样？

元数据写到临时文件并原子替换，成功才修改内存。图片先写入，失败可能留下无引用文件，但旧 JSON 仍然有效。上一版和自动备份提供恢复入口；这不是跨文件事务，更不代表验证了所有断电情况。依据：`ArchiveStore.atomicWrite/commit` 和失败测试。

## 为什么导入前要验证所有图片？

只验证角色列表会让引用缺失或不可解码的图像进入库。`inspectBackup` 检查格式、大小、角色字段和图片，然后导入才创建安全备份、写新图并提交。坏备份测试证明当前库不变。依据：[调用链](02-core-call-chains.md)。

## 怎样证明交付的是能运行的 App？

不仅运行类型检查和 11 项存储测试，还在 Electron 中完成两组桌面用例，再针对打包 `.app` 内的二进制重复两组验收，检查上传、重启、删除恢复、小窗口和透明图片。文件选择器返回值被固定，真实业务未模拟；未验证公证或其他平台。依据：[验证记录](evidence/verification.md)。

## 时间有限时优先改进什么？

先根据真实使用观察备份耗时和磁盘占用，只有出现需求才处理 [F01/F02](03-engineering-findings.md)。多用户、同步和跨平台不是当前目标。若用户要求向他人分发，再考虑签名公证。不能把 [路线图](04-optimization-roadmap.md) 中的建议说成已经完成。
